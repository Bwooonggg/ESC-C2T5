# Shared frontend unit testing plan

## Scope and oracle

This plan covers the shared login and session-control implementation used by the Worksheet and Parent Insight services in `frontend/src`. It also records the retained, non-overlapping unit coverage for shared API configuration, service clients, summary retrieval, screening, Worksheet client creation, and progress formatting. The current implementation is the test oracle. Each test isolates one unit and mocks only its direct outgoing dependencies.

The login scope includes Supabase client construction, the auth API, `LoginForm`, `ProtectedRoute`, `LoginPage`, `AccessDeniedPage`, login-related route wiring, and the Insights API authentication-failure event consumed by `ProtectedRoute`. The retained general frontend scope is listed separately in units U12 through U23. Service component behavior after authentication remains outside this plan.

Every table row is one separately reported Jest test. Test IDs use `UT-LOGIN-Uxx-xx`, where `Uxx` identifies one public unit or tightly coupled operation group. The plan contains **104 unit tests**: 70 login and authentication tests plus 34 retained, non-overlapping frontend tests.

## Isolation and naming rules

- Use dummy URLs, publishable keys, tokens, emails, and passwords. No test contacts Supabase or writes real credentials.
- Reset mocked modules when testing module-level environment decisions in `supabaseClients.ts`.
- Component tests use a memory router with an explicit initial path and route state.
- Deferred promises keep loading and submitting states observable without timers or network calls.
- Unmount every rendered component and restore window event listeners, globals, and mocks after each test.
- Supabase auth methods, React Router navigation, `getCurrentParent()`, and `fetch` are mocked only when they are direct dependencies of the target unit.

## Black-box techniques used

| Technique | Where used | Why it was chosen | Selection rule |
|---|---|---|---|
| Equivalence class testing | Service selection, environment configuration, Supabase results, credentials, route state, session presence, API paths and status classes, response envelopes, progress records, and dates | These inputs form categories that take distinct branches rather than useful numeric ranges. | Give each behaviorally distinct valid, absent, invalid, and dependency-failure class its own row. |
| Robust equivalence class testing | Missing environment values, missing sessions, wrong-service events, unsupported authorization statuses, rejected dependencies, non-JSON responses, empty progress data, and malformed dates | The implementation explicitly handles unexpected or incomplete values at its boundaries. These cases check that the feature fails closed, returns a deliberate empty result, or ignores unrelated input. | Select the closest meaningful invalid or unexpected representative for each boundary. |
| Decision table testing | Login submission, requested-path selection, protected-route rendering, and access-denied account switching | Outcomes depend on combinations such as service, session, authorization failure, dependency result, and requested path. | Cover every feasible rule that produces a distinct output or short-circuit point. |
| State transition testing | Form editing, submitting, retrying, auth-state changes, service changes, and component unmount | These units change visible state in response to events and asynchronous completions. A single input-output assertion would miss ordering and cleanup faults. | Cover each meaningful state transition and confirm obsolete listeners or promises cannot update the unit. |
| Normal boundary value analysis | Access-token length, required credential length, requested-route prefix, and API authorization statuses | The implementation changes behavior at an empty/nonempty string boundary, a service-path prefix boundary, and exact status values 401 and 403. Neighboring values can expose missing or over-broad comparisons. | Test string lengths 0 and 1, the value immediately before and at the route-prefix boundary, and statuses 400 through 404 around the two authorization values. |
| Robust boundary value analysis | Requested path just outside the intended service namespace | `startsWith("/insights")` also accepts a path such as `/insights-old`. This is outside the intended route namespace but is accepted by the current implementation, so it is a useful robust value and documents a likely redirect-validation gap. | Test a valid child path, the exact service root, a one-character-short prefix, and a prefix collision. Do not invent maximum credential lengths that the source does not enforce. |
| Loop enumeration | `Format.toChartRows()` and the skill-series identity maps | These units iterate over progress records and the complete skill-area collection. A representative item alone could miss a missing or incorrectly mapped skill area. | Exercise zero records, partial records, every defined skill area, and every seeded date-skill combination where the complete output shape matters. |
| Worst and robust-worst boundary value analysis | Not used | There are no independent numeric variables whose boundary combinations would be meaningful. Decision tables cover the dependent categorical conditions directly. | Do not create Cartesian products of equivalent service and error cases. |

## Deferred tests

| Deferred area | Reason and later test level |
|---|---|
| Real Supabase password authentication | Unit tests replace `signInWithPassword`, session reads, auth-state subscriptions, and sign-out. Credentials, token issuance, refresh, persistence, and project configuration need integration tests against dedicated test users. |
| JWT contents and backend authorization | The frontend treats the access token as opaque. Signature, issuer, expiry, and mapping to an application user belong to backend or end-to-end authentication tests. |
| Full browser-native email validation | Unit BVA checks the declared required-field lower boundary in jsdom. The complete browser email-validity algorithm, submission blocking, validation messages, and accessibility behavior still need Selenium or another browser-level test. |
| Cross-tab and storage persistence | Supabase owns local-storage synchronization and refresh coordination. Verify these with browser integration tests rather than replacing browser storage in unit tests. |
| Service component behavior after login | Worksheet generation and Parent Insight dashboard rendering have their own unit and integration scopes. This plan retains their shared client and formatting utilities but does not add component-level dashboard cases. |
| Live authorization-role mismatch | `LoginForm` probes `/me` for Insights and service APIs can return 403. The real account-to-role configuration requires an integration or end-to-end test. |

## Implementation prerequisites and constraints

| Item | Requirement |
|---|---|
| Component harness | Add `@testing-library/react` and `@testing-library/user-event`, or build an equivalent `react-dom/client` plus `act()` harness. Prefer accessible queries and user-visible behavior over component internals. |
| CSS imports | Configure Jest mappings for CSS modules and plain CSS before importing login components. The current Jest configuration does not map either form. |
| Router harness | Use `MemoryRouter` and small probe routes to observe navigation paths, replacement, and route state. Mock `Navigate` only when the target unit is route composition rather than navigation behavior. |
| Supabase module isolation | Mock `createClient` before importing `supabaseClients.ts`, reset modules between environment cases, and never allow a real client to start network activity. Because the module reads `import.meta.env` at import time, use a Vite-aware test transform or first extract a side-effect-free client factory if the current CommonJS Jest transform cannot isolate those values. |
| Deferred promises | Use explicitly controlled promises for pending login and session tests. Resolve or reject every deferred promise before cleanup to avoid open handles. |
| Event cleanup | Spy on `window.addEventListener`, `window.removeEventListener`, and `window.dispatchEvent` only around the target case; restore them after every test. |
| Existing tests | Units U12 through U23 describe the 34 retained Jest cases. Do not duplicate them when implementing U01 through U11. Keep the separate DAS7 Selenium suite because this unit plan does not replace browser-level coverage. |
